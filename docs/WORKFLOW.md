# 检查与试玩入口

使用项目根目录 `检查试玩.ps1`。默认不扫描所有未提交改动，不改用户存档，不提交或发布。

| 本次改动 | 命令 | 检查范围 |
|---|---|---|
| 全屏页面、孵化/交配 UI | `./检查试玩.ps1 -Scope ui` | 类型、构建、全屏交互、两种尺寸截图 |
| 战斗 HUD 与动作 | `./检查试玩.ps1 -Scope battle` | 类型、构建、战斗操作、两种尺寸截图 |
| 来访、分享、结缘 | `./检查试玩.ps1 -Scope social` | 来访规则、构建、双存档互访与孵化 |
| 玩法/宠物/地图规则 | `./检查试玩.ps1 -Scope rules` | 当前规则测试组、构建、战斗基本操作与重载 |
| 存档/个体迁移 | `./检查试玩.ps1 -Scope save` | 地图/遗传/结缘读档规则、构建、浏览器重载 |
| 仅重新构建试玩 | `./检查试玩.ps1 -Scope preview` | 类型、构建、启动与战斗基本检查 |

先查看将执行的步骤：任意命令加 `-Plan`，不会构建或修改结果文件。

按**本次**文件自动选择：
```powershell
./检查试玩.ps1 -Files assets/scripts/PMGame.ts -Plan
./检查试玩.ps1 -Files assets/scripts/PMModel.ts,assets/scripts/PMGame.ts
```
自动选择只是文件级分组；PMGame 或图片/场景改动会选全屏与战斗检查。单文件承载多个功能时，优先按实际任务明确选组，例如仅改来信应选 social。未知文件、工具或文档改动不会假装完成游戏检查，而是提示选择范围。

## 结果与停止条件
- 流程：类型检查 → 相关规则 → 构建 → 核对/启动原试玩服务 → 相关浏览器检查 → 输出原 URL。
- 任一步失败立即停止，查 `checks/workflow/latest.json` 的失败步骤和对应日志；修正后重跑受影响组，不自动无限重试。
- `status: passed` 只表示注册的自动检查通过；`visualReview: pending` 表示仍需查看报告中列出的新截图。最终回答分别说明自动检查、已看画面、用户待验收范围。
- 预览地址仍是 `http://127.0.0.1:8780/`。服务已在运行时核对页面与本次产物一致；端口不匹配时报错，不关闭别的进程。
- 浏览器测试使用独立上下文，长计时使用测试时钟。不要接入用户当前标签页注入测试存档。
- 本机路径集中于 `tools/workflow.config.json`。已有部分历史检查仍含本机路径/旧版本断言，未验证适用性前不要加入分组。此入口不是微信/抖音发布或真机验证。

## 新任务怎么使用
读交接卡 → 找模板/相关源码 → 实现当前需求 → 选相关检查 → 查看相关截图 → 给用户原试玩入口。必要时补充当前组遗漏的真实场景，不以组名代替覆盖判断。交付后只更新交接卡确实变化的事实。
